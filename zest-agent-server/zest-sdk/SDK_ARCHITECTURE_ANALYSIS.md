# SDK 架构分析
## 概述
`sdk` 并非轻量级模型包装层，而是一套围绕**会话(Conversation)、智能体(Agent)、大模型(LLM)、工具(Tool)、工作空间(Workspace)、插件(Plugin)、MCP** 构建的智能体运行时 SDK。
其设计目标：将大语言模型打造为**可管控的软件智能体**，具备工具调用、状态维护、会话持久化、本地/远程双模式执行能力，并可通过插件、钩子、外部工具协议实现能力扩展。

从对外 API 设计来看，该包刻意暴露**统一运行时外观门面**，而非仅提供单一窄域能力。根包导出了 `Agent`、`Conversation`、LLM、Tool、Workspace、Plugin 及 MCP 集成等核心抽象，这表明：**本 SDK 定位是智能体应用的完整运行底座**，而非仅用于快捷调用提示词的辅助工具库。

## 架构设计
架构层面采用**七层分层运行时设计**：

1. **门面层（facade layer）**
以 `sdk/__init__.py` 为入口，聚合高频公共接口，为使用者提供稳定统一的导入入口与对外门面。

2. **会话编排层（conversation orchestration layer）**
以 `BaseConversation`、`Conversation`、本地会话 `LocalConversation`、远程会话 `RemoteConversation` 为核心，是整个运行时的入口。
负责消息接收、运行生命周期、回调机制、执行状态、暂停/终止语义、会话标题生成，以及**本地执行与远程代理执行**的逻辑区分。

3. **智能体定义层（agent definition layer）**
以 `AgentBase` 为核心，定义智能体的组成结构：大模型、工具规约、MCP 配置、提示词配置、内容压缩器、评审器、上下文技能信息。
简言之，该层定义了智能体**静态与半静态固有能力**。

4. **状态与持久化层（state and persistence layer）**
以 `ConversationState` 会话状态、`AgentState` 智能体状态为核心，是项目关键架构设计决策。
不将智能体运行态仅驻留进程内存，而是**显式建模会话级共享状态、智能体级独立状态**，支持断点续跑、会话恢复、多智能体协同执行、事件历史持久化。

5. **执行能力层（execution capability layer）**
包含 LLM 抽象、工具注册中心、内置工具、MCP 工具、工作空间操作等。
智能体**推理思考、工具调用、命令执行、文件读写、外部系统交互**的实际能力均由该层提供。

6. **扩展层（extension layer）**
由插件、上下文、生命周期钩子、技能相关模块组成。
支持在不改动核心逻辑的前提下定制运行时：技能丰富提示上下文、钩子拦截生命周期流程、插件可将技能/钩子/MCP配置/智能体/命令打包为可复用扩展包。

7. **横切治理层（cross-cutting governance layer）**
包含事件、安全、可观测性、日志、评审、密钥管理等模块。
不承载核心业务能力，但贯穿所有执行链路，提供**链路追踪、安全管控、策略校验、运行诊断**能力。

整体架构定位偏向重型化设计：在一套运行时模型中统一了**执行调度、状态持久化、能力扩展、运行治理**四大核心能力。

## 功能组成
从功能维度，SDK 可划分为六大核心能力组：

### 1. 智能体运行与会话管理
系统核心中枢。用户创建智能体、挂载至会话、发送消息、驱动会话运行；SDK 自动调度模型、工具、事件、持久化机制完成任务闭环。

### 2. 模型抽象与推理管控
LLM 模块基于 LiteLLM 封装，提供统一模型适配接口，内置重试逻辑、厂商抽象、Token/计费元数据、流式输出、工具调用适配、模型能力兼容处理。

### 3. 工具执行与外部动作系统
工具包定义工具规约、运行时工具实例、注册发现机制、内置工具集；智能体可调用本地工具、SDK 注册工具、外部 MCP 服务提供的工具。

### 4. 状态恢复与多智能体支持
会话与上下文模块协同实现：会话状态持久化、智能体状态注册、事件日志、执行状态快照、智能体实例重建。
这是本 SDK 相较于普通简易智能体封装库**最大差异化优势**之一。

### 5. 扩展生态体系
插件、钩子、技能加载模块构成完整生态：插件可分发提示技能、生命周期钩子、MCP 服务配置、命令定义、智能体定义，支持以声明式方式定制部署能力。

### 6. 工作空间与环境集成
工作空间、IO、Git 相关模块，让智能体运行时可**标准化操作文件、执行命令、代码仓库交互**，并统一适配本地/远程运行环境语义。

## 模块拆解
从模块化视角，SDK 由多个内聚子系统构成：

### agent 智能体模块
定义智能体抽象与配置模型，回答核心问题：**智能体在启动执行前，具备哪些能力与提示上下文**。

### conversation 会话模块
定义会话协议、本地/远程运行时实现、会话状态、事件访问、生命周期方法、卡死检测、标题生成、执行流管控，是包裹智能体的**运行时外壳**。

### context 上下文模块
提供智能体系统高层上下文状态，重点包含智能体状态、技能、提示上下文、记忆集成；作为**静态配置**与**可恢复执行上下文**的桥梁。

### llm 大模型模块
统一模型接口与厂商适配逻辑，屏蔽各模型服务商差异，提供适配智能体工作流的运行时 API。

### tool 工具模块
定义工具规约、实体定义、结构范式、注册中心、内置工具集，是智能体**所有动作行为**的承载层。

### mcp 模块
对接外部 MCP 服务，将外部能力映射为智能体可直接调用的工具，扩展原生工具边界。

### plugin 插件模块
封装可复用运行时扩展，插件能力宽泛：可注入技能、钩子配置、MCP 服务、智能体、自定义命令，是 SDK 官方的**扩展分发标准**。

### workspace 工作空间模块
抽象智能体运行环境，标准化命令执行、文件操作、Git 仓库检视，统一抹平本地/远程运行差异。

### event 事件模块
提供事件模型与事件调度核心；运行时基于事件驱动，是可视化、持久化、回调通知、诊断排查、增量状态同步的基础。

### security 安全模块
风险研判与操作确认策略机制，用于管控智能体敏感工具操作，保障行为可治理、可拦截。

### observability / logger / critic / secret / io / git / utils
均为支撑型模块，不定义核心交互模型，但对**生产可用、问题诊断、序列化、持久化、运行正确性**至关重要。

## 核心业务流程
当前架构包含四大端到端核心流程：

### 流程1：构建并运行本地智能体会话
调用方初始化 LLM、创建智能体、绑定本地工作空间创建会话，工厂自动实例化 `LocalConversation`。
会话启动时：初始化/恢复会话状态、绑定事件中心、注册持久化与回调消费器、初始化插件运行态，最终通过智能体执行循环处理用户消息。

### 流程2：构建并运行远程智能体会话
调用方同样使用统一会话门面，仅传入远程工作空间，工厂返回 `RemoteConversation`。
本质为客户端代理模式：通过 HTTP/WebSocket 与远端运行时通信，本地镜像远端事件，对外保持与本地模式一致的调用接口。

### 流程3：从持久化状态恢复会话
运行时加载会话状态，基于智能体状态快照与智能体工厂机制**重建智能体实例**；架构天然支持断点续跑、暂停恢复、故障容灾场景。

### 流程4：运行时能力扩展
通过插件注入技能、钩子、MCP 配置、命令与智能体定义；工具通过注册中心或 MCP 桥接解析加载。
实现**新增能力无需修改核心编排逻辑**的可扩展运行时。

## 架构优势与潜在风险
### 架构核心优势
1. 分层清晰，具备长期演进能力，而非一次性脚本式实现；
2. 本地/远程执行基于同一会话模型统一抽象，接口无感知切换；
3. 显式会话状态、智能体状态建模，天然支持断点续跑与多智能体编排；
4. 插件、钩子、技能、MCP 多维度扩展，运行时可定制性极强；
5. 事件驱动架构，解耦各模块职责，便于可视化、持久化与链路追踪；
6. 工作空间抽象，屏蔽环境差异，为智能体提供稳定统一的执行载体。

### 潜在架构风险
1. `LocalConversation` 职责过于臃肿：包揽启动初始化、运行时组装、插件加载、事件订阅、持久化绑定、生命周期管控，存在**大上帝类**风险；
2. `RemoteConversation` 同样过重，混杂远程 API 客户端、WebSocket 通信、本地事件缓存、会话语义逻辑，职责耦合严重；
3. `AgentBase`、`ConversationState`、`AgentState` 均趋向巨型核心模型，复杂度高、理解成本大、后续变更风险高；
4. 扩展体系能力强大但概念冗余：内置工具/注册工具/MCP工具/插件/钩子/命令/技能能力重叠，新开发者上手理解门槛高；
5. 核心链路混入大量横切治理逻辑，提升生产可用性的同时，代码整体精简与轻量化难度变大。

## 可优化简化方向
当前代码已有部分向轻量化演进的趋势（如基于状态驱动重建智能体），仍有可优化空间：

1. **精简会话运行时职责**
`LocalConversation` 改造为纯门面层，将状态初始化、事件中心装配、插件管理、卡死检测、持久化绑定等逻辑拆分至专门的启动器、插件运行管理器、执行引擎。

2. **拆分远程通信职责**
将 `RemoteConversation` 拆解为：纯 API 客户端、WebSocket 事件流客户端、状态镜像缓存组件，降低调试与测试复杂度。

3. **分离配置快照与运行时状态**
当前 `AgentState` 混杂持久化配置快照、执行元数据、层级信息、阻塞动作可变状态；拆分为**智能体配置快照**与**智能体运行态**，降低认知负担。

4. **状态模型剥离持久化逻辑**
`ConversationState` 不应同时承载状态定义与存储恢复逻辑，抽离出持久化适配器/仓储层，实现职责分离。

5. **收敛扩展能力冗余**
统一内置工具、注册工具、MCP、插件、钩子、技能的能力编排管线，定义明确的优先级与加载规则，减少概念重叠。

6. **收敛对外核心概念模型**
精简对外心智模型，仅保留**会话、智能体、状态、能力、运行环境**五大核心对象，降低开发者上手成本。

## 总结
从架构定位来看，`zest-sdk/sdk` 是一套**完整的智能体运行时平台**，而非简易大模型调用 SDK。
核心设计思想：拆分**智能体定义、会话编排、执行能力、持久化状态**四大模块，通过事件机制与扩展点串联整体流程。

核心亮点：高可扩展性、运行时能力完备、本地/远程语义对齐、会话状态可恢复。
主要代价：部分编排模块职责过于集中、扩展体系概念繁杂带来复杂度提升。

下一阶段演进方向：**不删减核心能力，仅细化模块边界**——瘦身会话核心类、分层远程运行时、拆分配置快照与实时运行态、标准化扩展编排规则，在保留能力的同时大幅提升可维护性。
